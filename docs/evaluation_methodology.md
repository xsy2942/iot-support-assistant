# Agent 评测方法说明

## 为什么不直接写 100%

本项目最早的 100% 指标来自脚本生成的标准问题集。它适合做 sanity check，也就是证明数据、检索、路由和报告脚本能跑通，但不适合直接当成真实泛化能力。

原因很简单：问题由同一套模板生成，知识库字段也由同一套脚本生成，模型/检索器更容易命中关键词。这种结果可以保留，但必须标注为“生成集”或“链路验证集”。

## 更合理的评测拆分

当前项目把问答评测拆成两层：

| 数据集 | 文件 | 作用 |
|---|---|---|
| 生成集 | `eval/questions.csv` | 验证主链路是否可复现，覆盖 FAQ、错误码、历史工单和产品手册 |
| 挑战集 | `eval/challenge_questions.csv` | 检查口语改写、信息缺失、未知错误码、反事实干扰、高风险转人工 |
| 诊断集 | `eval/diagnostic_cases.csv` | 验证遥测规则诊断的分类、优先级和路由 |

## 当前指标口径

| 指标 | 含义 |
|---|---|
| Top3 召回率 | 预期证据是否出现在前三条召回结果里 |
| 路由准确率 | 是否正确判断直接回答、先追问或转人工 |
| 引用覆盖率 | 需要知识库回答的问题是否带了证据引用 |
| 严格证据匹配率 | 召回证据是否匹配预期设备型号或错误码 |
| 转人工识别准确率 | 高风险、未知码、投诉赔偿类问题是否拒绝强答并转人工 |
| 信息不足追问准确率 | 模糊问题是否先追问关键字段 |

## BadCase 怎么用

评测报告会把每条问题的实际路由、状态、证据和命中情况写入 `reports/agent_eval_report.json`。后续优化时不应该只看总分，而要抽取失败样例做 BadCase 分析：

- 口语改写失败：说明关键词和型号归一化不够。
- 严格证据不匹配：说明相似设备或相似错误码混入，需要加强元数据过滤。
- 该追问却回答：说明信息完整度判断太宽。
- 该转人工却回答：说明风险词、未知错误码或责任类语义识别不够。

## 和开源 Agent 项目的评测思路对齐

成熟 Agent 项目一般不会只报一个好看的准确率，而是强调：

- 可复现任务集：固定输入、固定预期输出、可重复跑。
- 挑战集或真实任务：用口语、噪声、边界条件检验泛化。
- 执行日志：保留 Agent 每一步 action / observation，方便追踪失败原因。
- 分项指标：检索、工具调用、路由、安全边界、成本/延迟分开看。
- 回归测试：每次改 Agent 策略后重新跑同一批问题，防止新版本退化。

本项目当前版本对应的是个人项目规模的轻量评测：有固定 CSV 测试集、可复现脚本、逐条 case 报告、ReAct trace 和 BadCase 分析入口。
